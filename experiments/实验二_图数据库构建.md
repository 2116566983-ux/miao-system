# 实验二 · 苗绣纹样图数据库构建

> **课程**：《数据采集与清洗》
> **学时**：6 学时（2 理论 + 4 实践）
> **对应单元**：第二单元「关系与图谱」
> **使用界面**：⑥ 知识图谱

---

## 一、这个实验要回答什么

**数据之间的关系，应该存在哪里？**

实验一让我们把「一张照片」变成了「一条记录」。
但记录和记录之间是有关系的：这张图派生自那张图，
这个纹样属于那个地域，这个地域有它常用的技法。

把这些关系存进**表格**，还是存进**图**？这就是本实验的命题。

---

## 二、预备知识

### 2.1 三种数据模型

| 模型 | 结构 | 典型系统 | 适合什么 |
|---|---|---|---|
| 键值 | key → value | Redis | 缓存、会话 |
| 关系型 | 表 + 外键 | MySQL / SQLite | 事务、报表、强一致 |
| 图 | 节点 + 关系 | Neo4j | 关系密集、路径查询 |

**本实验只讨论后两种**，因为本项目的痛点正好落在它们的差异上。

### 2.2 一个必须先想清楚的问题

假设你要存「这张图派生自那张图」。用表格怎么存？

```
表 images:
   image_id | file_name | source_image_id | ...
   color_12 | color_12.jpg | basic_3      | ...
```

`source_image_id` 这一列就是关系。它**能工作**。那问题在哪？

**试着回答这三个问题**：
1. 如果要查「basic_3 的所有后代」，怎么写？
2. 如果关系不止一层（basic_3 → color_3 → color_3_v2），怎么写？
3. 如果层级不确定（可能是 1 层也可能是 5 层），怎么写？

问题 3 是关键。SQL 里写变长层级，需要递归 CTE，
写法复杂且不同数据库语法不同。而在图数据库里，它是**一句话**：

```cypher
MATCH (root:Image {image_id: 'basic_3'})-[:DERIVED_FROM*1..5]->(d)
RETURN d.image_id
```

> **教学要点**：图数据库不是「更好的数据库」，
> 它是**为「关系本身就是查询目标」这个场景**设计的数据库。
> 把这话记住，就能判断什么时候该用图。

## 三、实验步骤

### 步骤 1：先看一遍完整的图模型（观察）

打开系统 → **⑥ 知识图谱** 标签页 → 板块一「图数据库的三个基本概念」。

**记录**：

1. 本项目用了哪几类**节点**？各多少个？
2. 用了哪几类**关系**？各多少条？
3. 节点总数和关系总数的比值是多少？说明了什么？

> 第 3 题的参考思路：如果关系数远多于节点数，
> 说明这份数据的「价值在连接上」——这正是它适合图数据库的信号。

### 步骤 2：理解「关系是一等公民」

同一页，板块一里讲到的第三个概念是「属性」。

**思考题**：
- 节点可以有属性（如一张图的宽、高）
- **关系能不能有属性？**

答案是**能**。在本项目里，`DERIVED_FROM` 关系就可以带一个属性
`处理方式: color`，说明这张变体图是**通过色调变换**得到的。

**对比**：如果用表格存，这个「处理方式」要放哪一列？
如果还想记「处理强度」「处理时间」「处理用的工具」呢？
是不是所有关系属性都得堆在一张表里，而大部分行这些列都是空的？

> 这就是图数据库的第一个优势：**关系可以有自己的属性**，
> 不需要为它单独建表。

### 步骤 3：Cypher vs SQL 正面对比

同一页，板块二「同一份数据，两种存法」，
找到对照表，逐行读一遍，然后对着板块三的预设查询做练习。

**任务**：对下表每一行，分别在两个代码框里找到对应写法，抄录下来。

| 查询 | Cypher | 等价的 SQL |
|---|---|---|
| 一朵纹样的全部变体 | | |
| 变体的变体（两跳） | | |
| 一张图的全部邻居 | | |

抄完后回答：
1. 哪个查询在两种写法里长度差异最大？
2. 为什么「邻居查询」在 SQL 里特别别扭？

> 第 2 题的思路：SQL 里 `(i:Image)-[r]-(other)` 这种
> **不知道关系类型、不知道方向**的查询，需要 union 所有可能的表，
> 而图数据库天然支持「任意关系、任意方向」。

### 步骤 4：跑真实查询

在板块三，逐个点击 6 个预设查询的「**执行查询（跑真实数据）**」按钮。

**记录每次返回的行数**，填入下表：

| # | 查询 | Cypher 要点 | 返回行数 | 你的解读 |
|---|---|---|---|---|
| ① | 一朵纹样的全部变体 | 一跳 | | |
| ② | 变体的变体 | `*1..2` | | |
| ③ | 一张图的全部邻居 | 无向 | | |
| ④ | 共色的图片 | 共享邻居 | | |
| ⑤ | 按地域统计 | 聚合 | | |
| ⑥ | 技法 × 地域 | 跨维度 | | |

**关键发现**：⑤ 和 ⑥ 会返回 **0 行**。

这不是系统坏了。页面会明确告诉你原因——
`region`、`technique` 这些字段**还没有标注**。

**写下一句话总结**：为什么「查不到数据」有时候不是错误，而是信息？

> **这是本实验最重要的认知**：
> 一个返回空结果的查询，告诉你的是「数据的完备性还不够」，
> 这本身就是有价值的结论。真实工作中，
> **会读懂空结果**和**会写查询**一样重要。

现在去 **⑤ 标注纹样** 标 5 组（填上地域、技法），
再回 ⑥ 重跑 ⑤⑥ 两个查询——**数据出现了**。

> 这个「标注 → 查询有结果」的闭环，是本实验的高潮。
> 它让学生亲眼看到：**数据的价值取决于它被补充的完整程度**。

### 步骤 5：动手写一个查询（进阶）

在板块三下方，基于已有数据自己写一个 Cypher 查询，要求：

- 至少用到一种本项目已有的节点标签
- 至少跨过一种关系
- 返回结果能回答一个**你真正好奇的问题**

**示例问题**（可自选）：
- 色彩变体一共用了哪些颜色？
- 哪个纹样组的变体最多？
- 有没有图片既没有颜色关系也没有形态关系？（数据完整性问题）

> 最后一个问题是**故意留给学生的**：它会引导学生发现
> 「数据里总有一部分是残缺的」，而**发现残缺正是清洗的开始**。

## 六、教师备课提示

### 本实验的两个高潮

**第一个高潮**：学生抄完 Cypher 和 SQL 对照，发现
「邻居查询」在 SQL 里要写 union，而在 Cypher 里就一行。
这个对比不需要老师总结，学生自己抄一遍就懂了。

**第二个高潮**：⑤⑥ 查询返回 0 行 → 去标注 → 回来有数据。
这个闭环让学生**亲眼看到数据被补充后的效果**，
比任何讲解都有说服力。

### 环境准备

| 方案 | 说明 | 适用 |
|---|---|---|
| A. 不装数据库 | 系统自动用 CSV 内存图，功能一样 | 学生机、机房 |
| B. 装 Neo4j | 学生自己装，看真实 Cypher 执行 | 技术拓展层 |

> **两种模式在界面上只差一行提示文字**，
> 查询结果结构完全一致。所以教学不受环境限制。

### 常见卡点

| 卡点 | 应对 |
|---|---|
| 学生问「0 行是不是错了」 | 反问：「如果字段都没填，应该返回几行？」 |
| 学生说 Cypher 语法像 SQL | 指出关键差异：`()-->()` 画的是**形状**，不是描述 |
| 学生不理解 `*1..2` | 画三层节点图，让他数「一跳能到哪、两跳能到哪」 |

## 附：完整 Cypher 参考

本实验用到的 6 个查询（也是 `app/graph_teach.py` 里的预设）：

```cypher
// ① 一朵纹样的全部变体
MATCH (src:Image {image_id: $iid})<-[:DERIVED_FROM]-(v:Image)
RETURN src.image_id AS 源图, v.image_id AS 变体, v.variant AS 类型
ORDER BY v.image_id

// ② 两跳：变体的变体（SQL 里需要递归 CTE）
MATCH (src:Image {image_id: $iid})<-[:DERIVED_FROM*1..2]-(v:Image)
RETURN DISTINCT v.image_id AS 变体, v.variant AS 类型
ORDER BY v.image_id

// ③ 一张图的全部邻居（方向未知、类型未知）
MATCH (i:Image {image_id: $iid})-[r]-(other)
RETURN type(r) AS 关系, labels(other)[0] AS 邻居类型,
       coalesce(other.name, other.image_id, other.group_id) AS 邻居
ORDER BY 关系

// ④ 共色的图片（共享邻居 = 反向推荐）
MATCH (a:Image {image_id: $iid})-[:USES_COLOR]->(c:Color)<-[:USES_COLOR]-(b:Image)
WHERE a <> b
RETURN c.name AS 共同颜色, count(DISTINCT b) AS 同色图片数
ORDER BY 同色图片数 DESC

// ⑤ 按地域统计纹样分布（需 region 已标注）
MATCH (g:MotifGroup)-[:FROM_REGION]->(r:Region)
OPTIONAL MATCH (g)-[:HAS_VARIANT]->(i:Image)
RETURN r.name AS 地域, count(DISTINCT g) AS 纹样组数, count(i) AS 图片数
ORDER BY 图片数 DESC LIMIT 20

// ⑥ 跨维度：技法 × 地域（需 technique 与 region 已标注）
MATCH (g:MotifGroup)-[:USES_TECHNIQUE]->(t:Technique)
OPTIONAL MATCH (g)-[:FROM_REGION]->(r:Region)
RETURN coalesce(r.name, '未标注') AS 地域, t.name AS 技法, count(*) AS 组数
ORDER BY 组数 DESC LIMIT 20
```
