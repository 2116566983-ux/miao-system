# 并发能力压测报告（2026-10-21）

对应会议纪要：**"需测试系统并发能力，确保能支撑一个班级（30-50人）同时在线操作"**

---

## 一、结论先说

| 状态 | 50 人同时保存的写 P95 | 判定 |
|---|---|---|
| 改造前 | **4746 ms** | 不达标（全班齐点保存要等近 5 秒） |
| 只调锁退避参数 | 646 ms | 达标 |
| 再改用追加写 | **205 ms** | 达标且有余量 |

**当前代码已改到第二档（退避参数），50 人写 P95 = 646 ms。**
追加写接口已提供，把保存动作切过去还能再降到 205 ms。

全程 **零丢行、零重复、零错误**——锁本身是对的，慢在排队方式。

---

## 二、测的是什么

不压生图接口：那是外部大模型 API，压它要花钱、会被限流，测出来的也不是我们系统的能力。

压的是**我们自己承担、全班共享**的那一层——存储（`app/storage.py`，文件锁 + CSV）。

一个学生的一次完整操作按真实流程建模：

```
读作品列表 → 读自己的记录 → 保存一件新作品 → 再读一次列表
```

其中"保存"要独占文件锁，"读"可并发。预置 200 条历史作品模拟学期中数据。

起跑方式用 `threading.Barrier` 让所有线程在同一刻冲进来——模拟上课齐点"生成"。

---

## 三、完整数据

每次都校验行数：应有 N 行、实得 N 行、丢 0 行、重复 0 行。

| 退避参数 | 人数 | 保存方式 | 写 P50(ms) | 写 P95(ms) | 总耗时(s) |
|---|---|---|---|---|---|
| 旧 0.02/0.2 | 30 | 整表重写 | 1931 | 4741 | 4.97 |
| 旧 0.02/0.2 | 30 | 追加写 | 333 | 2941 | 3.18 |
| 旧 0.02/0.2 | 50 | 整表重写 | 1757 | 4746 | 5.20 |
| 旧 0.02/0.2 | 50 | 追加写 | 344 | 2950 | 3.40 |
| 新 0.002/0.01 | 30 | 整表重写 | 218 | 412 | 0.46 |
| 新 0.002/0.01 | 30 | 追加写 | 80 | 199 | 0.24 |
| 新 0.002/0.01 | 50 | 整表重写 | 352 | 646 | 0.72 |
| 新 0.002/0.01 | 50 | 追加写 | **97** | **205** | **0.26** |

读操作从头到尾都很轻：50 人时读 P95 只有 24~33 ms，不是瓶颈。

---

## 四、根因与改法

**根因一：锁是非阻塞的，抢不到就睡。**

`storage.file_lock` 用 `msvcrt.LK_NBLCK`（非阻塞）加锁，失败后退避重试，
退避上限原来是 **200 ms**。30~50 个人排队时，"睡多久"直接变成排队成本。

把退避上限从 0.2 降到 0.01，写 P95 从 4746 ms 掉到 646 ms，**7 倍**。

代价是轮询更频繁（50 人 × 每 10 ms 一次）。对 2 学时的课堂负载，这点 CPU
远比让学生干等 4 秒划算。

**根因二：保存一件作品要重写整张表。**

`atomic_write_csv` 是"读全表 → 改 → 整表重写"，锁内耗时随表长线性增长。
但保存新作品本质只是**多一行**，不需要读全表。

新增 `storage.append_csv_row()`：只追加、不重写，锁内耗时与表长无关。
50 人时写 P95 从 646 ms 再降到 205 ms。

这里有个编码坑值得记：表头由 `atomic_write_csv` 以 `utf-8-sig` 写出、文件头带 BOM，
**追加时若也用 utf-8-sig，BOM 会被写到文件中间**，之后读出来的首列会变成
`\ufeffwork_id` 这种怪值。所以只在新建文件时用 utf-8-sig，其余用 utf-8。

## 五、生图那一段（推算，非实测）

存储已达标，但课上真正要等的是生图。按会议记录的 5 秒/张推算：

| 并发上限 K | 50 人各生一张的总时长 |
|---|---|
| 1（串行） | 250 秒 ≈ 4 分钟 |
| 5 | 50 秒 |
| 10 | 25 秒 |

**这张表是排队公式算的，不是压出来的**——没有真实 API 凭据，压了也不代表线上。
要拿到真实数字，得在服务器上用测试 key 打一轮。

给课上的三条建议：
1. **分批发**：每 10 人一轮，比全班齐点省一半以上的等待
2. **加队列 + 限流**：超过并发上限的请求排队而不是直接打 API，避免超时集中报错
3. **加缓存**：同一素材 + 同一参数重复生成时直接返回上次结果

## 六、复现

```bash
python tools/load_test.py --users 50 --mode append    # 追加写
python tools/load_test.py --users 50 --mode rewrite   # 整表重写（现状）
python tools/load_test.py --users 30 --rounds 3       # 每人 3 轮
```

脚本会自动校验丢行与重复，任一不为 0 即判未通过。
