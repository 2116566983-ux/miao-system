**项目**：「数采淬美·赛创融合」——《数据采集与清洗》课程图数据库教学模块
**数据载体**：苗绣纹样
**文档版本**：2026-10-13

## 一、项目概述

### 1.1 做什么

依托《数据采集与清洗》课程，以苗绣纹样为真实数据载体，把图像数据整理、
图数据库建模、纹样检索、数字化重组和作品展示纳入同一条教学实践链路。

### 1.2 完整链路

```
采集与登记 → 清洗与标注 → 图数据库组织 → 可视化检索
                              → 纹样提取 → AI 辅助重组 → 作品展示与评价
```

### 1.3 系统实现状态

| 环节 | 状态 | 说明 |
|---|---|---|
| 图像数据整理 | ✅ 已完成 | 1000 张图片全量体检，元数据 25 字段 |
| 纹样提取 | ✅ 已完成 | 绣品照片 → 纹样符号（透明 PNG + 2D 连续 + 3D 立体网格） |
| 纹样标注 | ⏳ 待人工 | 任务表已备好（245 组），需人工填写 |
| 图数据库建模 | ✅ 已完成 | 10 类节点、14 类关系，含导入脚本；已在本地 Neo4j 5.26 实测导入（1279 节点 / 4739 关系） |
| 可视化检索 | ✅ 已完成 | Streamlit 界面，双数据源（真实 Neo4j 已验证连通） |

**结论：技术链路已全部打通，剩余瓶颈是标注数据的人工填写。**

### 1.4 一个容易被忽略的命题：采的到底是什么数据

数据集里是**绣品实物的照片** —— 靛蓝土布 + 彩色绣线 + 黑边 + 拍摄光照。
但课程研究的「纹样」是一个**符号 / 特征**：

- 照片里混着底布、黑边、光照、拍摄角度，这些都不是纹样本身的信息
- 纹样应该是可提取、可比较、可复用的——同一个花枝可以绣在任何底布上
- 只有把它分离成带透明通道的图案，才能进标注体系、进图数据库、进 AI 重组

`app/motif_extract.py` 做的就是这件事（详见第七章）。

## 二、数据集分析

### 2.1 实测结果

对 `archive/byx` 的 1000 张图片全量分析：

| 指标 | 结果 |
|---|---|
| 文件总数 | 1000 张 jpg |
| 总大小 | 155 MB |
| 坏图 | **0 张** |
| 色彩模式 | 全部 RGB |
| 尺寸种类 | 402 种，跨度 91×51 至 5472×3648 |

### 2.2 关键发现：不是 1000 个独立样本

| 前缀 | 数量 | 实际内容 |
|---|---|---|
| `basic` | 250 | 原始图/裁剪图 |
| `texture` | 250 | 同源 resize 版本 |
| `color` | 250 | 与 texture 尺寸完全相同，色彩变体 |
| `mixup` | 250 | 拼贴合成图（多尺度叠加） |

**命名规律**：文件名序号 `% 4` 与变体严格对应
（0=basic, 1=texture, 2=color, 3=mixup），
**250 组、每组 4 张，校验零例外**。

**结论：这是 250 张原图 × 4 种变体，不是 1000 个独立样本。**

这一发现直接决定了两个设计决策，见第四、五节。

### 2.3 质量分布

| 状态 | 数量 | 处理方式 |
|---|---|---|
| 可标注 | 731 | 正常进入标注流程 |
| 拼贴图 | 245 | 标记不可标注（含多尺度内容） |
| 尺寸过小 | 24 | 标记不可标注（最小 91×51） |

其中 `basic` 可标注 **241 张**。

### 3.2 双数据源设计

系统启动时自动探测环境，**无需配置即可运行**：

| 状态 | 检索 | 生成 | 说明 |
|---|---|---|---|
| 图数据库 + ComfyUI | ✅ 图查询 | ✅ | 完整功能（当前状态） |
| 任一缺失 | ✅ | 视情况 | 自动降级 |
| 都没有 | ✅ CSV | ❌ | 检索照常可用 |

**设计意图**：教学工作不能因为某个服务没启动就中断。
即使 Neo4j 和 ComfyUI 都不可用，检索环节依然完整可用。

**一条踩过的坑**：本地图库清单 `metadata/images.csv` **始终加载**，
不随数据库状态切换。它服务的是 ④ 提取纹样、⑤ 标注纹样 这些
按文件路径工作的页面，与图数据库无关。早期版本让它随数据库状态
变为 `None`，导致 Neo4j 一连上、提取页的分组选择器就消失了。
详见 §6.5.6 缺陷三。

### 3.3 视觉设计：为什么不能用通用配色

这一节的结论来自一次前端返工——界面初版能跑，但「一看就是 AI 生成的模板」。
问题不在功能，在**视觉语言与主题无关**。

#### 三个具体症状

| 症状 | 原状 | 为什么是问题 |
|---|---|---|
| emoji 堆砌 | 47 处 `🚀 ✂️ 🎉 📌 💡` | 模板化界面的典型指纹；emoji 在同一行里大小不一、颜色杂乱 |
| 通用调色板 | `#38bdf8` `#10b981` `#f59e0b` | 这是 Tailwind 默认色，和苗绣没有任何关系 |
| 彩色圆角卡片 | 浅蓝/浅黄/浅绿底 + 4px 圆角 + 粗左边线 | 卡片把视线从内容（纹样）上抢走 |

#### 解决：从数据里取色，而不是从调色板里挑

配色不是「选几个好看的颜色」，而是**给这套材料定色**。
数据集自己给出了答案——`metadata/images.csv` 的 `dominant_color` 实际分布：

| 颜色 | 数量 | 对应材料 |
|---|---|---|
| 墨黑 | 436 | 部分绣品的黑色填充边 |
| **朱红** | 112 | 绣线，苗绣最醒目的红 |
| 浅灰 | 140 | 布面高光 |
| 桃红 | 52 | 绣线 |
| **靛蓝** | 52 | 土布底色 |
| **藏青** | 36 | 土布（浸染更深） |
| 明黄 | 16 | 绣线 |

于是色卡按**材料**定名，而不是「主色/辅色」：

| 名称 | 色值 | 用途 |
|---|---|---|
| 靛蓝土布 | `#243b53` | 主按钮、副标题、正文强调 |
| 朱砂绣线 | `#a8352a` | **仅**用于警示与章节标记 |
| 银饰 | `#c9d1d9` | 边框、分隔线 |
| 素纸 | `#f8f7f4` | 页面底色（不用纯白） |

#### 一条关键取舍：红色不设为主色

初版把朱砂设为 `primaryColor`，结果**所有主按钮都是大红**，
整页显得焦躁，而且红色迅速贬值——到处都是红，就没有重点了。

现在：**靛蓝做主色**（稳，且是这套数据的底色），
**朱砂只给警示和章节标记**（出现在真正需要停一下的地方）。
一个颜色值不值得用，取决于它出现的频率。

#### 排版上的三条规则

1. **一条竖线代替彩色卡片**——`.note` / `.caution` / `.done`
   都是「3px 左边线 + 极淡底」，不用圆角、不用投影
2. **缩略图固定高度 + `contain`**——混排竖图/方图时网格才对齐；
   用 `cover` 会裁掉纹样主体（本数据集竖图多，一裁就是花心）
3. **Markdown 表格必须一次性提交**——表头与数据行分两次
   `st.markdown` 调用时，Streamlit 会把数据行原样当文本输出

> **第 3 条是实测踩出来的**：⑥ 知识图谱页的节点类型表一度
> 渲染成原始 Markdown 源码。306 个单元断言全部通过、
> UI 无头检查也全部通过——但它们都**不会检查 Markdown 是否真的渲染成表格**。
> 是截图时人眼看出来的。
>
> 这就是 `tools/shoot_ui.py` 存在的理由：**必须真的看一眼**。

涉及文件：`app/theme.py`（样式与色卡）、
`.streamlit/config.toml`（Streamlit 原生控件配色）、
`tools/shoot_ui.py`（视觉走查截图）。

#### 第二遍走查：改完之后又发现的四处

第一次改完「emoji 清零 + 换色卡」并不等于改完。逐页截图人眼过一遍时，
又抓出四类**机械替换漏掉的地方**——它们都有同一个特征：
**不是没改，而是改得不彻底**。

| 漏掉的地方 | 表现 | 根因 |
|---|---|---|
| ③ 我的作品 | 作品缩略图是竖构图，`width="stretch"` 撑满栏宽后拉成一根高柱，右侧空出一大片灰底，两件作品就占满一屏 | 只有「网格」用了 `.thumb` 定高盒，**单列布局**那处被漏掉了 |
| ② 已选素材条 | 最多 6 张横排，竖横图混排时下方编号一条高一条低 | 同上——不在网格分支里 |
| ⑤ 标注页「机器线索」 | `background:#fffbeb; border-radius:8px` 硬编码 Tailwind 琥珀色 | 它不是 `.note/.caution/.done` 三者之一，**不在批量替换的匹配范围里** |
| `.streamlit/config.toml` | 每次启动打一条 `"server.gatherUsageStats" is not a valid config option` | 键放错段位（应在 `[browser]`），**不报错，只警告**，最容易留下来 |

**共同教训**：批量替换（正则换 emoji、换色值）只能处理**形状一致**的
目标。凡是「长得很像但结构不同」的地方——单列布局、非标准色块、
配置文件里放错段的键——都会静默漏网。所以清完之后必须**逐页截图复核**，
而且要做**两遍**：第一遍看整体风格，第二遍专门找「这一类还有没有别的」。

#### 新增一档：`.hint`（机器线索）

改完之后发现 `.note` / `.caution` / `.done` 三档不够用。
⑤ 标注页的「机器线索」面板需要一个**第四档**语义：

- 用 `.note`（平静的靛蓝）→ 机器结论看起来像客观事实
- 用 `.caution`（朱砂警示）→ 整块变红，像是「出错了」，但机器没出错

教学上这个区别很要紧：**不能让机器结论看起来像权威指令**。
所以给它旧纸的黄褐色（`#fbf7e8` 底 / `#b58900` 左边线），
语气是「机器这么猜，你自己看」，而不是「你要小心」。

这也解释了为什么红色不能到处用：一旦朱砂被滥用成通用强调色，
就再也无法通过颜色区分「这是警告」和「这只是个提示」。

### 3.4 关键技术决策

#### 决策一：ComfyUI 任务必须异步处理

ComfyUI 的任务是**异步队列**，提交后不会立即返回结果。

如果界面用同步方式等待，会**卡死几十秒**，学生以为系统坏了。

因此对接层拆成三步：

```
submit()        → 返回 prompt_id，立即响应
poll(pid)       → 查询状态，不阻塞
fetch_images()  → 完成后取回结果
```

界面上的「查询进度」按钮对应这个设计。

#### 决策二：工作流模板必须校验占位符

**这是测试中发现的真实缺陷。**

如果教师选了"多纹样组合"但误配了单图模板，早期版本会
**静默产出一张只用了一张图的"组合"作品，不报错**。
教师会以为融合生效了。

修复方式：`require_placeholders()` 在提交前校验，缺失即报错并列出
模板中实际含有的占位符，便于定位。

该缺陷已加回归测试锁住。

## 四、图模型设计

### 4.1 节点与关系

**节点（10 类）**

| 节点 | 说明 | 数据来源 |
|---|---|---|
| `Image` | 图片（含全部变体） | 自动生成 |
| `MotifGroup` | 纹样来源分组 | 自动生成 |
| `Motif` | 纹样元素 | 待 Label Studio 标注 |
| `Color` / `Form` / `Technique` / `Region` | 颜色/形态/技法/地域 | 待人工标注 |
| `GeneratedWork` | 学生生成作品 | ComfyUI 产出 |
| `Student` | 学生 | 课程名单 |
| `CourseTask` | 课程任务 | 课程安排 |

**关系（14 类）**

```
(:Image)-[:BELONGS_TO]->(:MotifGroup)        图片归属分组
(:Image)-[:DERIVED_FROM]->(:Image)           变体派生链路
(:Image)-[:CONTAINS]->(:Motif)               图片包含纹样
(:Image)-[:USES_COLOR|HAS_FORM|USES_TECHNIQUE|FROM_REGION]->(...)
(:GeneratedWork)-[:DERIVED_FROM]->(:Image)   作品派生来源
(:GeneratedWork)-[:COMBINES]->(:Motif)       作品组合的纹样
(:GeneratedWork)-[:CREATED_BY]->(:Student)   作者
(:GeneratedWork)-[:SUBMITTED_FOR]->(:CourseTask) 提交任务
```

### 4.2 核心决策：为什么需要 `MotifGroup`

这是项目中最关键的设计决策。

**问题**：4 个变体是同一张苗绣的不同版本。若直接作为平行节点：

1. 检索时同一张苗绣出现 4 次，学生看到 3/4 是重复内容
2. 标注工作量虚高清空，实际只需标 250 次而非 1000 次

**方案：双轨表达**

| 机制 | 解决的问题 |
|---|---|
| `MotifGroup` 节点 | **检索聚合**（每组只出代表图）+ **属性继承** |
| `DERIVED_FROM` 关系 | **数据溯源**（版权链路）+ **教学深度**（路径查询） |

两者都不能省：前者给学生用，后者给技术层和版权追溯用。

### 4.3 关键设计：标注属性挂在 `MotifGroup` 而非 `Image`

**这是"不用重构"能真正成立的唯一原因。**

验证结果（已实测）：

```
标注 3 组 → merge → 12 行自动继承（每组 4 个变体全部带上）
```

也就是说：

- 人工标注 **250 次**，而非 1000 次
- 将来调整字段口径，**只改一处**，不用改 1000 条记录

**如果当初把地域、技法直接挂在 `Image` 上**，回填时要重复标 4 遍，
改口径要改 1000 条。这才是"会返工"的真正来源。

## 五、标注体系

### 5.1 为什么是 245 组

250 组中，5 组因原图尺寸过小由其他变体代替，故为 245 组。

### 5.2 字段设计

**11 个待填字段**，前 4 个为必填级：

| 字段 | 必填级 | 说明 |
|---|---|---|
| `pattern_type` 纹样类型 | ✅ | 决定检索主维度 |
| `region` 地域来源 | ✅ | 苗绣地域性极强 |
| `technique` 刺绣技法 | ✅ | **无法由像素推断，必须人工** |
| `dominant_color` 主色调 | ✅ | 人眼判断，勿用机器值 |
| `symmetry_type` 对称形式 | 加分 | 机器有参考值 |
| `composition` 构图特征 | 加分 | |
| `cultural_meaning` 文化寓意 | 加分 | **涉及民族文化，不确定就留空** |
| `permission_note` 来源与授权 | 加分 | **关系到能否公开展示** |
| `quality_note` 质量备注 | 加分 | |
| `pattern_type_detail` 纹样细类 | 加分 | |
| `usage_suggestion` 适用说明 | 加分 | |

**8 个机器参考字段**（`ref_` 前缀）：主色、配色、对称度、明度、饱和度、疏密程度。

### 5.3 关于机器参考值的诚实说明

**主色参考值不可直接采信。**

实测发现：这批图多为实物拍摄，**普遍带黑色边框或暗背景**，
机器统计出的首位色常常是背景色而非纹样主色。

例：`basic_8` 实为深绿底 + 桃红花卉刺绣，机器报"黑色+浅灰+桃红"。

**处理方式**：已做两项改进（背景剔除、修正色名映射使深色不误判为黑），
但仍不够准确。因此**将该字段定位降级为"色彩分布提示"**，
表头明确标注「常为背景，勿直接采信」。

**为什么不再继续调算法**：图片主色本就需要人眼判断，
继续堆启发式只会让代码越来越复杂且仍不可靠。
明确标注"这个值不可靠"比给一个看似专业的假数值更有用。

**对称、明度、疏密三项参考值相对可靠**，但对称度受拍摄角度影响也有偏差。

### 5.4 标注方式：从填 CSV 改为网页点选

**这是本系统在易用性上最关键的一次调整。**

原始设计是「导出 CSV → 人工填 → 命令行 merge 回去」。问题在于：

- 目标用户是**公选课学生（非计算机专业）**
- 245 行 × 11 列的 CSV，用 Excel 填，容易因编码、逗号、换行把文件弄坏
- 学生要自己在文件夹里找图，来回切换
- 结果：标注数据长期为 0，检索界面的地域/技法/色彩筛选**全是空的**

因此新增 **④ 标注纹样** 标签页，把标注搬进界面：

| 环节 | 原方式 | 网页方式 |
|---|---|---|
| 看素材 | 自己按文件名找图 | 页面直接显示大图 |
| 选取值 | 手打，易写错 | 下拉选项来自指南推荐取值 |
| 机器参考 | 对照另一张表的列 | 显示在图片旁边 |
| 保存 | 存 CSV + 跑命令行 | 点一下按钮 |
| 协作 | 无归属信息 | 记录标注人与时间戳 |
| 进度 | 不确定 | 顶部进度条 + 每人工作量 |

**数据结构**（`annotation/annotations.csv`）：

```
group_id（主键） + 11 个标注字段 + annotator + updated_at
```

以 `group_id` 为主键，而不是图片编号——这样标一次即覆盖该组全部 4 个变体，
与图模型「标注属性挂 `MotifGroup`」的设计保持一致。

**合并**：界面底部「教师操作用」→「合并到检索数据」，
调用 `AnnotationStore.merge_to_images()`，按组展开回写 `images.csv`。

**已验证链路**（测试段 10、11）：

- 按组 upsert，同组重复提交不产生重复行
- 空字符串不计入已填
- 回写时该组 4 个变体全部继承，未标注组不受影响
- 标注前按地域筛不出结果，标注后能筛出该组全部 4 个变体

### 5.5 教学结合

标注过程本身就是**第一单元的实验**。学生学到的不是填表，而是：

- 数据从哪来
- 字段怎么定义
- **不确定时怎么处理**（留空还是猜测）

网页方式还额外带来一个教学价值：**进度与工作量对每个人可见**，
天然形成协作压力，也让教师能按标注量分配任务。

## 六、纹样提取（把符号从照片里分离出来）

模块：`app/motif_extract.py`。**只用 numpy + PIL**，不引入 opencv/scipy
——课程环境是学生自己的笔记本，依赖越少越容易装起来。

### 6.1 要解决什么

| | 照片里的东西 | 是不是纹样本身 |
|---|---|---|
| 底布 | 靛蓝土布 / 墨绿 / 近黑 | ✗ 背景 |
| 黑边 | 照片四周的填充条 | ✗ 拍摄产物 |
| 光照 | 明暗不均的拍摄光 | ✗ 拍摄产物 |
| **绣线图案** | 花枝、配色、针脚 | **✓ 这才是纹样** |

### 6.2 算法流程

```
照片 → ①去黑边 → ②估底布 → ③分割 → ④清噪 → ⑤裁剪 → 透明 PNG
```

**① 去黑边** `trim_black_bars()`
逐行/逐列判断是否为「近黑 + 高度均匀」，是则裁掉。
数据集里部分照片是「正片 + 黑条」的形式。

**② 估底布** `estimate_cloth()`
取图像外圈几像素的环带，算中位色作为底布色，并用 IQR 统计色差波动范围。
为什么用外圈：布总是铺到画面边上的。

**③ 分割** `build_mask()` —— 这是最关键的一步，**前 6 版都失败在这里**：

| 尝试 | 思路 | 为什么失败 |
|---|---|---|
| 1 | 全局 RGB 距离阈值 | 底布本身有渐变，一刀切不掉 |
| 2 | HSV 色相判定 | 近黑底布**没有可靠色相** |
| 3 | 饱和度判定 | 白线饱和度低，被误判成底布 |
| 4 | 亮度假定「底布暗绣线亮」 | 靛蓝底布比部分绣线还亮 |
| 5 | 边缘密度 | 光滑的靛蓝面边缘也少，区分不开 |
| 6 | **局部粗糙度 + Otsu + 颜色约束 + 边缘连通** | ✅ 稳定 |

最终方案的四条约束（缺一不可）：

```python
rough = local_roughness(small, radius=rough_radius)   # 绣线有起伏纹理
thr = max(_otsu_threshold(rough), 3.0)                 # 自适应阈值
cloth_similar = color_dist < seed_tol                  # 颜色要接近底布
bg_candidate = (rough <= thr) & cloth_similar
bg_small = _connected_from_border(bg_candidate)        # 只认与边缘连通的
```

- **局部粗糙度**：用积分图算每个像素邻域的方差。绣线有针脚起伏，
  底布平滑 —— 这个特征比颜色稳，因为它测的是**纹理**不是**颜色**。
- **Otsu 阈值**：自动找到双峰分布的分界，不用手调。
  （注意：平台上 `argmax` 会取到最左，所以取**平台中点**。）
- **颜色约束**：防止把画面上其他平滑区域（如另一块布）当成背景。
- **边缘连通**：只保留与画面边缘连通的背景。纹样内部的小孔
  （花瓣间的空隙）不与边缘连通，因此被正确地保留为前景。

**④ 清噪** `clean_mask()` + `_largest_components()`
用 PIL 的 Max/Min 滤波做开闭运算去毛刺，再按连通块面积排序保留最大的几块。

**⑤ 裁剪** `crop_to_content()` → 输出带 alpha 的 PNG。

### 6.3 一个必须记住的教训

**「花瓣被挖空了」是假警报。**

basic 系列里不少纹样的花瓣本身就是**白线**。放白底上看，
白线白底糊成一片，视觉上像「花瓣中间是空的」。
第一版据此判定算法有 bug，白白改了三轮。

**正确做法：在棋盘格底上看图。** 因此 `checkerboard()` 成为正式接口，
界面里「② 透明纹样」视图也固定用棋盘底。
这个教训写进代码注释，避免下次再犯。

### 6.4 四种展示形态

提取出的纹样是一个 `(RGB array, alpha mask)` 二元组，界面提供四种看它的方式：

| 函数 | 输出 | 表达的命题 |
|---|---|---|
| `checkerboard()` | 棋盘底 | 透明 ≠ 挖空，只是没底色 |
| `tile_preview()` | 镜像四方连续 | 符号可**无限复用** |
| `relief_field()` + `relief_mesh()` | **有厚度的三维网格** | 刺绣是**实物**，有体积 |
| `heightmap()` | 归一化高度图（0–1） | 降级用：无 plotly 时的静态起伏 |

> `tile_preview()` 默认**已合成底色**返回（`backdrop=(248,248,246)`）。
> 因为四方连续是判断「拼接效果」的，透明图在深色界面上会变成一片黑，
> 接缝反而看不见了。需要透明时显式传 `backdrop=None`。

### 6.5 3D 立体展示：从「一张曲面」到「一件实物」

**第一版的做法是错的**，值得记下来：

```
高度图 heightmap()  →  go.Surface(z=高度, colorscale="copper")
```

三个根本缺陷：

1. **`go.Surface` 不是真 3D。** 它本质是一张"弯曲的纸" ——
   没有厚度、没有侧面、没有背光面，凑近看永远是一层壳。
2. **高度图把 `alpha=0` 的区域强制归零**，纹样成了"浮在虚空里的碎片"，
   边缘垂直坠落。
3. **高度只取明度**。而苗绣大量是「同色系平绣」，线迹明度几乎一致，
   归一化之后只剩噪点 —— **起伏完全没结构**。这才是「没有 3D 效果」
   的真正原因，不是渲染参数的问题。

**现在的做法**，分三步：

#### ① `relief_field()` —— 双尺度高度场

| 尺度 | 信号 | 作用 |
|---|---|---|
| 粗尺度 | 距纹样边缘的距离（多步腐蚀近似，再开方） | 决定**大形状**：中心厚、边缘薄，形成浮雕坡面 |
| 细尺度 | 明度，且**先强模糊 3.0** | 只做**温和的表面起伏** |

融合权重 `0.72 * dist + 0.28 * lum`。

> **刻意不用「局部标准差/边缘项」。** 这个信号在真实绣品照片上几乎全是
> 噪点，权重稍大就把画面变成一丛尖刺（实测渲染出来像珊瑚/石笋）。
> 浮雕要的是"光滑坡面 + 温和纹理"，不是把每个像素的高低差都立起来。

#### ② `relief_mesh()` —— 有厚度的三角网格

生成正面 + 背面 + 外侧面，`mesh` 顶点自带 `vertexcolor`，所以 3D 出来
是**彩色的纹样**而不是一片灰。

两个关键细节：

- **边界柔化**：先 `GaussianBlur(1.6)` 得到软边界，高度乘
  `clip(taper * 3.2, 0, 1)`，让侧壁高度从中心到边缘连续变化。

- **「规则栅格 + 高度归零」，而不是「格子内/外 + 竖侧壁」**：
  最初按格子的 4 个角是否在纹样内来分情况、只给"部分在内"的格子补
  竖直侧壁，结果轮廓上出现一排高低不齐的**梳齿** —— 因为格子是粗的，
  边界格子被整块抬起。改成：只要格子沾到纹样，就整格生成正/背面；
  因为高度在边界已衰减到 0，边界格子的正面与背面会在 z 上**自然闭合**。
  轮廓完全由高度场决定，于是跟着高度场一起平滑。

  另外侧壁只为「本格有纹样、相邻格没有」的边生成（原来无条件生成
  4 面，三角数多 3 倍，纯浪费）。**53k → 21.4k 三角面**。

#### ③ `build_3d_figure()` —— 完整场景

孤立的一张曲面悬在虚空里，大脑无法判断它的大小、朝向和空间关系，
所以「看起来不像 3D」。必须有：

```
展示台地板 + 台面网格线（尺度参照）
+ 环境光/定向光（明暗对比）
+ 透视相机（可自由旋转/缩放/平移）
```

支持 `style="light"/"dark"` 跟随页面主题，避免亮色页面上出现一块突兀的黑背景。

界面侧（④ 提取纹样）还做了：

- **3D 视图提到第一位作为默认视图**，不再是藏在子选项里还要再点一次按钮。
- **三个可调参数**：网格精细度 / 网格密度 / 浮雕厚度。
- **缓存**：`_build_3d_payload` 用 `@st.cache_data`，参数以下划线开头
  （`_arr_bytes`）使其不参与哈希 —— 大数组哈希很慢，只按轻量参数命中缓存。
- **降级**：无 plotly → 退回灰度高度图 + 提示 `pip install plotly`，
  不允许因为缺一个可视化库就让整页崩掉。

> **开发工具**：`tools/render_mesh_preview.py` 是一个自制的
> z-buffer + 朗伯光照软件光栅化器，把同一份网格渲染成 PNG，
> 用来肉眼判断厚度/明暗/轮廓。这是本次能快速迭代的关键 ——
> 否则 3D 效果只能靠浏览器，改一版看一版成本太高。

## 六·五、图数据库：从「讲概念」到「真的跑起来」

### 6.5.1 这一章要解决的问题

项目的第 ⑥ 个标签页「知识图谱」承担的是**教学任务**：让学生在动手查纹样
的过程中，自然理解「图数据库和表格到底差在哪」。

但教学页如果只是贴几张示意图，学生是没有体感的。所以这一页的设计原则是：
**所有结论都由真实数据现场算出来**，而不是预先写死。

### 6.5.2 双数据源：教学不能依赖环境

| 模式 | 触发条件 | 数据来源 |
|---|---|---|
| 图数据库模式 | Neo4j 可连接 | `bolt://localhost:7687` 真实 Cypher |
| CSV 兜底模式 | 驱动缺失 / 连不上 / 无密码 | `graph/csv/*.csv` 内存建图 |

两种模式**返回结构完全相同**，界面上只有一行小字提示当前数据源。
这样即使学生机没装 Neo4j，整堂课也能照常上——
这是教学软件必须有的鲁棒性。

`app/graph_teach.py` 里的 `CsvGraph` 类是 CSV 路径的实现。
它**不是**要模拟 Neo4j，而是为了让界面在没有数据库时也能跑通，
并保证同样的查询语义。

### 6.5.3 教学内容：三个板块

| 板块 | 内容 | 设计意图 |
|---|---|---|
| 一、三个基本概念 | 节点 / 关系 / 属性，各配一句苗绣场景的解释 | 先建立最小知识框架 |
| 二、同一份数据，两种存法 | 表格 vs 图的对照表（6 行）+ Cypher/SQL 并排 | 破除「图数据库只是另一种数据库」的误解 |
| 三、动手查询 | 6 个预设查询，一键执行并显示真实返回 | 让结论从数据里长出来 |

**6 个预设查询**（每个都同时给出 Cypher 和等价的 SQL，并解释为什么图上更自然）：

| # | 问题 | 考察的图能力 |
|---|---|---|
| ① | 一朵纹样的全部变体 | 一跳关系 |
| ② | 变体的变体（两跳） | `*1..2` 变长路径 |
| ③ | 一张图的全部邻居 | 无向遍历、`type(r)` |
| ④ | 共色的图片 | 共享邻居（反向推荐） |
| ⑤ | 按地域统计纹样分布 | 聚合 |
| ⑥ | 技法 × 地域 | 跨维度 |

其中 ② 是最有说服力的一条：SQL 里要写死 JOIN 层数，图上用 `*1..2`
一句话就能问「两跳之内所有变体」。

**⑤⑥ 在当前数据下返回 0 行**——这不是 bug，而是刻意的教学素材。
`region` / `technique` 字段还没标注，所以按它们分组自然分不出东西。
页面专门写了提示：**「数据不完整本身就是《数据采集与清洗》要处理的问题」**，
并引导学生去 ⑤ 标注纹样 补上属性，回来这里立刻就有数据。
**一个返回空结果的查询，比一个返回漂亮结果的查询更贴近真实工程。**

### 6.5.4 本地 Neo4j 部署（实测记录）

**为什么装在本机**：服务器只剩 1GB 内存，Neo4j 的最小堆配置
（1GB heap + 512MB pagecache）会和 ComfyUI 抢内存，有把生图服务
OOM 掉的实际风险。本机 15.7GB 内存，富裕得多。

**安装**：Neo4j 社区版 5.26.0，解压到 `C:\Users\21165\miao-neo4j\`。
需要 Java 17（Temurin 17.0.20.1 已具备）。

> 一个环境上的坑：`dist.neo4j.org` 被 CloudFront 按国家封锁，
> 下载返回 `403 configured to block access from your country`。
> 换第三方镜像（`we-yun.com`）取得 ZIP。

**启动方式——绕开官方包装脚本**：

官方 `bin\neo4j-admin.bat` 与 `neo4j.bat` 在本机全部失败，且**报错被吞掉**，
只剩一个乱码 `WriteErrorException`。它们实际是转调 `.ps1`，
PowerShell 层把真实错误埋了。

排查后发现三层原因，逐条解决：

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | PowerShell 只回一个乱码错误 | 包装层吞掉了真实报错 | 直接调 Java 入口 |
| 2 | `Required environment variable 'NEO4J_HOME' is not set` | 包装层会自动设该变量，绕过它就没人设了 | 手动 `export NEO4J_HOME` |
| 3 | `Argument --home-dir is required` | `CommunityEntryPoint` 不读环境变量 | 显式传 `--home-dir` / `--config-dir` |

最终可用命令（报错完整可见）：

```bash
export NEO4J_HOME="C:/Users/21165/miao-neo4j/neo4j-community-5.26.0"

# 设初始密码——必须在首次启动数据库之前
java -cp "lib/*" org.neo4j.cli.AdminTool dbms set-initial-password <密码>

# 启动服务器
java -cp "lib/*;conf" \
  -Dserver.directories.neo4j_home="$NEO4J_HOME" \
  org.neo4j.server.CommunityEntryPoint \
  --home-dir "$NEO4J_HOME" --config-dir "$NEO4J_HOME/conf"
```

> 注意 `AdminTool server console` **走不通**：会抛
> `IllegalStateException: The supplied execution context is not an enhanced
> execution context`——`console` 子命令依赖包装层提供的增强上下文。
> 必须直接用 `org.neo4j.server.CommunityEntryPoint`（在 `neo4j-5.26.0.jar`）。

启动脚本已固化为 `tools/start_neo4j.bat`，双击即可，关窗即停库。

`conf/neo4j.conf` 适配本机的保守配置：

```
server.memory.heap.initial_size=1g
server.memory.heap.max_size=1g
server.memory.pagecache.size=512m
```

### 6.5.6 排查出的三个真实缺陷

接入真实数据库后暴露了三个此前被 CSV 兜底掩盖的问题，值得记录：

**缺陷一：参数名撞车**

`def run(q, **p)` 的第一个参数叫 `q`，而 Cypher 里有 `$q`（quality_status）。
位置传参 + 关键字传参直接抛
`TypeError: got multiple values for argument 'q'`。
首参改名为 `cypher`。

> 这是本项目**第二次**栽在同类问题上——此前 `CsvGraph._add_node` 也因
> 参数名与关键字撞车出错。教训：**参数名不要用单字母**。

**缺陷二：检索页的 schema 与导入脚本不一致**

`neo4j_client.py` 查的是
`(g:MotifGroup)<-[:BELONGS_TO]-(i:Image)`，
但导入脚本只建了 `HAS_VARIANT`；且 `markable`、`is_source`、`file_name`、
`aspect`、`mode`、`file_size_kb` 等属性根本没写入。

症状极具迷惑性：**`available=True` 但「纹样组数」显示 0**。
因为一直用 CSV 兜底，这个不一致从未暴露。

解法：Image 导入段补齐 8 个属性，并**同时建立两条方向相反的关系**——
`HAS_VARIANT`（组→图，教学页用）和 `BELONGS_TO`（图→组，检索页用）。
它们表达同一事实，保留两条是为了不破坏任何一处既有代码，代码里已加注释说明。

**缺陷三：本地清单与数据库状态被错误耦合**

原代码 `csv_df = None if DB_OK else load_csv(...)`——
意味着 Neo4j 一旦连上，`csv_df` 就成了 `None`。
但 ④ 提取纹样 页要读本地图库清单才能列出可选分组，
于是 `ex_path` 恒为 None，「开始提取纹样」按钮**根本不渲染**。

`tools/check_ui.py` 抓到了这个回归（`[FAIL] 找不到「开始提取纹样」按钮`），
但更值得注意的是它的**入口本身**：这次 UI 无头测试的价值，就在于
它是在「Neo4j 已连接」这个真实新状态下跑的。

解法：**`csv_df` 始终加载**。它只是本地清单文件，加载成本极低，
而且 ④⑤ 两个页面本来就按文件路径工作，与图数据库无关。
新增语义明确的 `db_search = bool(DB_OK)` 只给 ① 检索页用。
修复后 UI 检查里下拉框从 9 个变成 10 个——提取页的分组选择器回来了。

## 七、工作流与生成

### 7.1 两套工作流（4 个模板文件）

两种**创作模式**，各自准备两种**模型架构**的模板，共 4 个文件：

| 模式 | 模板文件 | 需要的模型 |
|---|---|---|
| 单图重组 | `img2img_template.json` | 整合检查点 |
| 单图重组 | `img2img_qwen.json` | 分离式（UNET + CLIP + VAE） |
| 多纹样组合 | `multi_motif_template.json` | 整合检查点 |
| 多纹样组合 | `multi_motif_qwen.json` | 分离式（UNET + CLIP + VAE） |

**为什么要两套架构**：不同环境装的模型不一样。服务器上只有分离式模型、
本地可能只有整合检查点。启动时盘点实际可用模型，逐模板核对它引用的
具体文件名是否存在，挑出匹配的那一套——**换环境不用改代码**。

### 7.2 占位符机制

工作流模板用占位符标记可调参数：

| 占位符 | 位置 |
|---|---|
| `__INPUT_IMAGE__` | 主纹样 LoadImage |
| `__INPUT_IMAGE_2__` | 第二张纹样 LoadImage |
| `__POSITIVE__` / `__NEGATIVE__` | CLIPTextEncode |
| `__SEED__` | KSampler 种子 |
| `__DENOISE__` | KSampler 创作强度 |
| `__BLEND__` | ImageBlend 融合比例 |

教师替换工作流时，只需在 ComfyUI 里标好占位符，
用 `Export (API Format)` 导出覆盖模板文件。

### 7.3 过程可追溯

每件作品记录以下字段，满足方案要求：

`work_id` / `student_id` / `mode` / `source_images` / `prompt` /
`negative_prompt` / `seed` / `denoise` / `blend` /
`model_or_workflow` / `workflow_file` / `created_at` /
`output_path` / `review_status` / `review_note`

**原始素材、提示词、模型或工作流、生成时间、作者——五项俱全。**

### 7.4 课堂部署

| 环节 | 位置 | 学生需要安装 |
|---|---|---|
| ComfyUI + 模型 | 教师端 GPU 机器 | 无 |
| Streamlit 系统 | 同上 | 无 |
| 学生电脑 | — | **只需浏览器** |

**省去每人 6.5GB 模型下载**，且工作流预先固定，避免课堂现场出问题。

### 8.1.1 界面无头测试

仅验证「服务能启动」是不够的 —— Streamlit 脚本只在浏览器连接时才执行，
所以 HTTP 200 证明不了页面逻辑正确。`tools/check_ui.py` 用官方
`AppTest` 无头跑完整页面：

| 检查项 | 内容 |
|---|---|
| 运行期异常 | 捕获未定义变量、API 误用等 |
| 错误提示 | `st.error` 数量应为 0 |
| 控件盘点 | 六个标签页（含提取页、知识图谱页）与各控件是否都渲染 |
| **端到端标注** | 填表 → 提交 → 落盘 → 逐字段校验 |

运行：

```bash
python tools/check_ui.py
```

> **踩过的坑**：Streamlit 表单内的控件在提交前不随 rerun 更新。
> 自测脚本设完值必须**直接提交**，中间不能插 `run()`，否则选择会被冲掉
> —— 第一版测试就因此误报成"应用有 bug"。

> **这个测试的真实价值**：它抓到过一个只在「Neo4j 已连接」时才出现的
> 回归（提取页按钮消失，见 §6.5.6 缺陷三）。说明无头测试必须在
> **多种真实环境下都跑一遍**，只跑默认状态会漏掉整类问题。

### 8.2 测试发现的真实缺陷

| # | 缺陷 | 严重性 | 处理 |
|---|---|---|---|
| 1 | 标注合并静默失败 | **高** | 中文表头与英文 key 不匹配，填了 3 组却报"进度 0%"。已加映射与列名校验 |
| 2 | 多纹样模板缺占位符时静默通过 | **高** | 会产出"假组合"作品。已加校验与报错 |
| 3 | 组内张数显示错误 | 中 | 筛选顺序导致显示 3 而非 4。已拆分为两个字段 |
| 4 | 主色预判 72% 报"黑色" | 中 | 背景主导 + 色名误判。已改进并**诚实降级该字段定位** |
| 5 | `image_root` 作用域错误 | **高** | 先点第二个标签页会崩溃。已提到外层 |
| 6 | 连接失败原因误报为 502 | 中 | 系统代理拦截了本地请求，却显示"服务返回 502"，误导排查方向。已改为区分「未启动」与「被代理拦截」 |
| 7 | ModelScope 返回 data URI 时解析失败 | 中 | 只认 https 链接，导致误报"返回体里没有图片数据"。已兼容 |

**缺陷 1、2、5 都是"不报错但结果是错的"类型**，最危险。
这正说明自动化测试的必要性。
